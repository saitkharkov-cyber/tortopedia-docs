# ChatGPT — основные правила рабочего процесса

> **Как использовать документацию:** в начале нового чата обязательно читать этот файл полностью. `CHATGPT_WORKFLOW_REFERENCE.md` не нужно читать целиком заранее — обращаться к нему по мере возникновения конкретной ситуации. Если какое-либо правило требует подробного толкования, примеров или исключений, использовать соответствующий раздел справочника.

---

## 1. Назначение

Этот документ фиксирует короткий набор обязательных правил взаимодействия:

**user → ChatGPT → user**

Главная формула:

**понять → проверить → предложить один шаг → получить подтверждение → изменить минимально → проверить результат → только потом коммит/отправка.**

Подробные пояснения, примеры и исключения находятся в `CHATGPT_WORKFLOW_REFERENCE.md`.

---

## 2. Язык

Основной язык общения и внутренней документации — **русский**.

Англицизмы использовать только там, где они являются буквальными техническими терминами, именами команд, файлов, технологий, API или элементов интерфейса.

Если есть точный и естественный русский эквивалент — использовать его.

---

## 3. Маленькие шаги

По умолчанию работать пошагово:

1. определить текущую точку;
2. предложить один следующий шаг;
3. дождаться подтверждения;
4. выполнить или дать точную команду;
5. проверить результат;
6. перейти дальше.

`+`, `++`, `+++` означают подтверждение **текущего предложенного шага**, а не бессрочное разрешение на последующие действия.

---

## 4. Не расширять границы задачи

Не делать «заодно»:

- рефакторинг;
- архитектурные изменения;
- переименования;
- очистку соседнего кода;
- обновление зависимостей;
- исправление посторонних проблем.

Если найдена отдельная проблема — указать её и не исправлять без согласования.

**Минимальное достаточное изменение предпочтительнее большого улучшения.**

---

## 5. Сначала проверка, потом изменение

Если состояние можно проверить — не строить решение на предположении.

Основной источник истины:

1. фактическое состояние файлов и Git;
2. подтверждённые решения текущей сессии;
3. актуальная документация/контрольная точка;
4. HANDOFF;
5. память о прошлых чатах.

Если память или HANDOFF расходятся с текущими файлами — верить текущим файлам и Git.

---

## 6. PowerShell и ручные правки

Для Windows-проектов команды давать только в fenced-блоках `powershell`.

Жёсткое правило:

**PowerShell-команда по умолчанию должна быть в одну строку.**

Не использовать here-string, если можно обойтись обычной однострочной командой.

Связанные атомарные действия можно объединять через `&&`.

Если нужно изменить файл вручную, явно писать:

> В редакторе открой...

Не смешивать ручную правку с PowerShell.

---

## 7. Git перед коммитом

Перед каждым коммитом обязательно:

```powershell
git diff --check
```

затем просмотр содержательного diff и:

```powershell
git status --short
```

Добавлять в индекс конкретные файлы. Без необходимости не использовать:

```powershell
git add .
```

или:

```powershell
git add -A
```

Намеренно неотслеживаемые файлы не добавлять, не удалять и не «чистить».

---

## 8. Главенство пользователя при коммите и отправке

Коммит и отправка изменений в удалённый репозиторий выполняются **только по явной команде пользователя**.

ChatGPT может:

- предложить коммит;
- подготовить команду;
- предложить сообщение;
- проверить diff и Git status.

Но сам запуск коммита или отправки допустим только после явного разрешения на конкретное действие.

`+`, `++`, `+++` считаются таким разрешением только тогда, когда непосредственно перед ними был предложен именно конкретный коммит или отправка.

Разрешение не переносится автоматически на следующие операции.

---

## 9. Source и сгенерированные файлы

Если проект работает по схеме:

**исходники → сборка → production**

обычно изменяем исходники, затем запускаем сборку/публикацию.

После автоматизации обязательно проверить фактический результат и `git status`.

Успешное завершение команды ещё не означает, что результат правильный.

---

## 10. HANDOFF

HANDOFF — стартовый снимок состояния для нового чата, а не постоянный источник истины.

В начале нового чата:

1. прочитать HANDOFF;
2. восстановить контекст;
3. сверить его с фактическим состоянием;
4. определить один следующий шаг.

Во время активной сессии HANDOFF постепенно теряет силу: новые подтверждённые изменения имеют приоритет.

Перед переходом в новый чат HANDOFF обновляется по текущему состоянию.

---

## 11. Защита от внезапного разрыва чата

Нельзя надёжно предсказать достижение лимита длины чата.

Поэтому для длинных активных сессий используется:

`CURRENT_SESSION_STATE.md`

Это короткая живая контрольная точка.

Обновлять её:

- после заметного этапа;
- после важного решения;
- после коммита/отправки;
- перед рискованной длинной серией действий;
- перед паузой;
- когда накопилось много нового контекста.

ChatGPT должен сам предлагать обновить такую контрольную точку, не дожидаясь конца чата.

После внезапного разрыва приоритет:

1. файлы и Git;
2. свежий `CURRENT_SESSION_STATE.md`;
3. актуальный HANDOFF;
4. документация;
5. память.

---

## 12. Пауза означает паузу

Если пользователь говорит:

- «стоп»;
- «подожди»;
- «пока не делай»;
- «останавливаемся»;

дальнейшие действия по этой ветке прекращаются.

---

## 13. Один ответ — один основной шаг

В пошаговом режиме не давать длинную цепочку команд наперёд.

По умолчанию:

- краткое объяснение;
- один следующий шаг;
- одна команда или одна ручная правка.

Исключение — пользователь явно просит полный план.

---

## 14. Не выдавать непроверенное за готовое

Нельзя говорить «готово», «исправлено», «всё работает», если результат ещё не проверен.

Правильнее:

> изменение внесено; теперь проверим результат.

---

## 15. Codex

Codex пока не входит в стандартный рабочий процесс.

Если возникнет реальная задача, где он даст явное преимущество, его использование сначала согласовывается отдельно.

После появления практики оформить отдельный `CODEX_WORKFLOW.md`.

---

## 16. Документация — часть проекта

Повторяющиеся полезные правила выносить из чатов в документацию.

Важное знание не должно существовать только в истории переписки.

---

## Короткая формула

**Не угадывать то, что можно проверить.**

**Не менять то, что пользователь не просил менять, без согласования.**

**Не коммитить и не отправлять изменения без явной команды пользователя.**
