# START SESSION — Tortopedia

> **Это единственная точка входа в любую рабочую сессию Tortopedia.**
>
> Новый чат всегда начинается с чтения этого файла. Не начинать с HANDOFF, памяти или немедленных изменений.

---

## 1. Локальная структура проекта

Основной сайт:

```text
D:\Git\tortopedia
```

Документация хранится внутри дерева проекта как отдельный вложенный Git-репозиторий:

```text
D:\Git\tortopedia\docs
```

Удалённые репозитории:

- сайт: `saitkharkov-cyber/tortopedia`;
- документация: `saitkharkov-cyber/tortopedia-docs`.

Папка `docs/` должна быть добавлена в `.gitignore` основного сайта. Поэтому локально это одно дерево проекта, но Git-истории остаются раздельными.

Нельзя смешивать команды Git двух репозиториев. Перед Git-командой всегда понимать, в каком каталоге она выполняется.

---

## 2. Что читать в начале сессии

Всегда:

1. полностью прочитать `START_SESSION.md`;
2. полностью прочитать `CHATGPT_WORKFLOW_RULES.md`;
3. если существует `CURRENT_SESSION_STATE.md` — прочитать его;
4. если работа продолжается из предыдущего чата или после длительной паузы — прочитать актуальный `HANDOFF.md`;
5. `CHATGPT_WORKFLOW_REFERENCE.md` использовать по мере необходимости, а не читать целиком автоматически;
6. если задача связана с подготовкой или редактированием статей — прочитать `TORTOPEDIA_CONTENT_STYLE_GUIDE.md`.

После чтения документации сверить её с фактическими файлами и Git. При расхождении приоритет у текущих файлов и Git.

---

## 3. Обязательный стартовый контроль

Перед изменениями проверить основной сайт:

```powershell
git status --short
```

При необходимости:

```powershell
git log --oneline --decorate -3
```

Если в текущей задаче меняется документация, отдельно проверить Git внутри `docs/`.

Не начинать изменения, пока не понятны:

- текущая ветка;
- существующие незакоммиченные изменения;
- текущая задача;
- один следующий шаг.

---

## 4. На всю активную сессию включить контроль CURRENT_SESSION_STATE.md

Это не действие «на конец чата», а постоянный контроль во время длинной активной работы.

ChatGPT обязан сам отслеживать необходимость обновления `CURRENT_SESSION_STATE.md` и не ждать напоминания пользователя.

Проверять необходимость обновления:

- после заметного этапа;
- после важного решения;
- перед длинной или рискованной серией действий;
- после commit/push, если работа в этой сессии продолжается;
- перед паузой, после которой планируется продолжить текущую сессию;
- когда накопилось много нового контекста;
- если с последнего обновления произошло несколько значимых изменений.

Практический внутренний вопрос после каждого заметного этапа:

> Если чат оборвётся прямо сейчас, `CURRENT_SESSION_STATE.md` позволит без догадок продолжить работу?

Если нет — предложить обновить его сейчас.

---

## 5. CURRENT_SESSION_STATE.md и HANDOFF — разные задачи

`CURRENT_SESSION_STATE.md` — живая контрольная точка текущей активной сессии.

`HANDOFF.md` — передача контекста следующему чату или после длительной паузы.

Практическое правило:

- сессия продолжается → поддерживать `CURRENT_SESSION_STATE.md`;
- работа на текущий период завершается и контекст передаётся дальше → обновить `HANDOFF.md`;
- если в конце сразу готовится актуальный HANDOFF, отдельное финальное обновление `CURRENT_SESSION_STATE.md` не требуется.

HANDOFF не является стартовым документом. В нём должно быть только напоминание начать с `START_SESSION.md`.

---

## 6. Приоритет после внезапного разрыва

1. фактические файлы и Git;
2. свежий `CURRENT_SESSION_STATE.md`;
3. актуальный `HANDOFF.md`;
4. остальная документация;
5. память о прошлых чатах.

---

## 7. После восстановления контекста

Не выдавать длинный план без необходимости.

Определить один следующий шаг, предложить его пользователю и ждать подтверждения согласно `CHATGPT_WORKFLOW_RULES.md`.
